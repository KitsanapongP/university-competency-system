# แผนรายงานผลการประเมินผู้เรียนแบบความเรียง - Version 1.1

วันที่: 2026-10-05
สถานะ: แผนสำหรับ Implement ต่อจากระบบรายงานปัจจุบัน
เอกสารต้นทาง: [Version 1.0](./learner-assessment-report-implementation-plan-v1.0.md), [แผนเดิม](./learner-assessment-report-implementation-plan.md), [Development Tickets เดิม](./learner-llm-report/implementation-plan.md)

## 1. เป้าหมายและลำดับการใช้เอกสาร

เปลี่ยนรายงานในหน้าประวัติส่วนตัวจากการ์ดสรุปรายข้อเป็นรายงานความเรียงที่อ่านต่อเนื่อง เชื่อมข้อค้นพบกับหลักฐาน ความหมาย และคำแนะนำที่ทำได้จริง ใช้สำนวนสุภาพเหมือนอาจารย์ให้คำแนะนำแก่ผู้เรียน

Version 1.1 มีผลแทนข้อกำหนดด้านรูปแบบเนื้อหา Output และ UI ของ Version 1.0 เท่านั้น กฎข้อมูล สิทธิ์ การคำนวณ และอายุรายงานยังใช้ตาม Version 1.0 และโค้ดปัจจุบันที่แก้ไขแล้ว

เอกสารนี้เป็นแผนงาน ยังไม่ใช่การแก้ Production Code และไม่ให้ถือว่า Release Gate ผ่านก่อนทดสอบกับ Ollama จริง

## 2. สิ่งที่พบจาก Codebase

- `apps/backend/services/assessment_observations.go` สร้างข้อค้นพบจากข้อมูลที่ Backend ตรวจแล้ว โดยแยก `strength`, `limitation`, `neutral` และมี `observation_id`, `FactType`, `Values`, `EvidenceRefs`
- `assessment_prompt.go` ส่ง `verified_observations` ให้ LLM ปัจจุบันให้เลือกไม่เกิน 3 รายการต่อหมวด และจำกัดข้อความแต่ละภาษาไว้ 240 ตัวอักษร
- `assessment_output_validator.go` ตรวจ JSON, หมวดที่อนุญาต, ID, สองภาษา, ความยาว, PII และการกล่าวอ้างตัวเลข/เกรด จากนั้นประกอบผลกับข้อเท็จจริงที่ Backend สร้าง
- `assessmentReadinessExplanation` ใน `assessment_observations.go` เป็นผู้สร้างข้อความสรุปความพร้อม ไม่ได้ให้ LLM ตัดสินผลใหม่
- `LearnerAssessmentReportPanel.jsx` ใช้ `ReportFindings` แสดง Title, Fact, Explanation และ Advice เป็นการ์ด ทำให้เนื้อหาซ้ำและอ่านเหมือนรายการข้อมูล
- รายงานและ Snapshot อยู่ใน JSON ของ `ai_learner_reports`; `ai_report_jobs` รองรับ Worker, Lease, Retry และ Progress อยู่แล้ว
- รุ่นปัจจุบันใน `assessment_source_hash.go` คือ Pipeline `learner-assessment-v1.0.3`, Prompt `learner-assessment-prompt-v1.0.4`, Output Schema `learner-assessment-output-v1.0.2`
- ค่าเริ่มต้นของ Context Budget ในโค้ดคือ Context 4096, Output Reserve 1024, Safety Margin 128 tokens แต่ค่าที่ใช้งานจริงอาจถูก override ผ่าน Environment ต้องตรวจค่าที่ resolve แล้วก่อนประเมินรุ่นใหม่

การเพิ่มความยาวใน Prompt อย่างเดียวไม่พอ ต้องเปลี่ยน Schema, Validator, งบ Output, การแสดงผล และ Version Hash ให้สอดคล้องกัน

## 3. Business Rules ที่คงไว้

- Go คำนวณผลตรวจความพร้อมและคะแนนทั้งหมด; LLM มีหน้าที่อธิบายและแนะนำ ไม่อนุมัติสิทธิ์ไปสหกิจ
- รายวิชา เกรด คะแนนหลัก และคะแนนเสริมใช้ข้อมูลก่อนเทอมที่เลือก รวม Summer และใช้เกรดดีที่สุดภายในจุดตัดเดิม
- กิจกรรมและคะแนนกิจกรรมใช้ข้อมูลล่าสุดทั้งหมด ต้องระบุขอบเขตนี้ในรายงาน
- ใช้เฉพาะแหล่งคะแนนที่พร้อม ไม่อ่านคะแนนที่ต้องคำนวณใหม่เป็นคะแนนปัจจุบัน
- ข้อมูลที่ไม่มีหรือยังไม่พร้อมไม่เท่ากับศูนย์ ไม่เท่ากับไม่มีทักษะ และไม่ใช่ข้อจำกัดส่วนบุคคล
- ไม่มีเกณฑ์สหกิจที่เปิดใช้งานยังวิเคราะห์ส่วนที่พร้อมได้ โดยระบุว่ายังตรวจความพร้อมไม่ได้
- ไม่มีหลักฐานเลยแสดงข้อมูลไม่เพียงพอ โดยไม่เรียก LLM
- ไทยและอังกฤษอยู่ในรายงานฉบับเดียว; เปลี่ยนภาษาไม่สร้างงานใหม่
- เก็บฉบับสำเร็จล่าสุดแยกเทอม 1/2 เปิดรายงานที่ล้าสมัยแล้วสร้างใหม่และซ่อนเนื้อหาเก่าตาม Flow เดิม
- การสร้างใหม่ด้วยข้อมูลเดิมเว้น 5 นาที; คงการป้องกันงานซ้ำและตรวจ Source Hash ก่อนบันทึก
- ใช้ Ollama `qwen3:4b`; ยังไม่เพิ่มการแนะนำอาชีพ, RAG, Embedding หรือการจัดอันดับสายงาน

## 4. Pattern การเขียนรายงาน

เป้าหมายเมื่อมีข้อมูลเพียงพอคือประมาณ 4-6 ย่อหน้า แต่ไม่บังคับจำนวนขั้นต่ำเมื่อหลักฐานมีน้อย แต่ละย่อหน้ามีประเด็นหลักเดียว ประกอบด้วยประโยคต่อเนื่อง 2-4 ประโยคตามความเหมาะสม ไม่ใช่ประโยคเดียวที่ยืดยาวจนอ่านยาก

| หัวข้อ | ผู้สร้างเนื้อหา | รูปแบบและจุดประสงค์ |
| --- | --- | --- |
| ภาพรวมความพร้อมก่อนสหกิจศึกษา | Backend | 1 ย่อหน้า อธิบายผลรวม จุดที่ถึงเกณฑ์/ยังขาด/ยังไม่มีผล และความหมายของการตรวจความพร้อม |
| จุดแข็งที่มีหลักฐานรองรับ | LLM จากข้อค้นพบที่อนุญาต | 0-2 ย่อหน้า เชื่อมสิ่งที่ถึงเกณฑ์กับการเตรียมตัว โดยไม่ขยายเป็นความสามารถที่ไม่มีหลักฐาน |
| แนวทางพัฒนาหรือเตรียมตัวต่อ | LLM จากข้อค้นพบที่อนุญาต | 0-1 ย่อหน้า ระบุสิ่งที่ทำต่อได้ พร้อมเหตุผล; มีคำแนะนำได้แม้ผ่านทุกเกณฑ์ |
| ข้อสังเกตจากการเรียนและกิจกรรม | LLM จากข้อค้นพบ `neutral` | 0-1 ย่อหน้า เลือกข้อสังเกตที่มีความหมาย ไม่ไล่แจกแจงเกรดทุกเทอมหรือสรุปบุคลิก |
| ขอบเขตและข้อจำกัดของการประเมิน | Backend | 1 ย่อหน้า อธิบายข้อมูลที่ใช้ จุดตัดรายวิชา ขอบเขตกิจกรรม และข้อมูลขาดพร้อมเหตุผล |

Pattern ของย่อหน้าวิเคราะห์: **ข้อค้นพบ -> หลักฐานที่รองรับ -> ความหมายอย่างระมัดระวัง -> แนวทางทำต่อเมื่อเกี่ยวข้อง**

ข้อกำหนดภาษา:

- อ่านเป็นรายงานต่อเนื่อง ไม่แสดง Fact ตามด้วย Explanation ที่พูดเรื่องเดียวกันซ้ำ
- ไม่เรียกการผ่าน GPA ว่ามีทักษะการเขียนโปรแกรมสูง หากไม่มีหลักฐานทักษะดังกล่าว
- คะแนนสะสมไม่มีเกณฑ์เปรียบเทียบจึงไม่เรียกว่าเก่ง/อ่อน/สูงกว่าคนอื่นหรือคิดเป็นคะแนนเต็ม 100
- เกรดต่ำกว่า A ไม่เป็นข้อจำกัดโดยอัตโนมัติ; ข้อจำกัดที่ยืนยันได้ต้องมีเกณฑ์จากระบบรองรับ
- แยกคำว่า “ยังไม่ผ่านเกณฑ์” ออกจาก “ยังมีข้อมูลไม่พอสำหรับวิเคราะห์”
- หากผ่านทุกเกณฑ์ ให้คำแนะนำเตรียมตัวต่อได้โดยไม่สร้างจุดอ่อนขึ้นมา
- คำแนะนำระบุว่าเป็นข้อเสนอ เช่น “อาจเริ่มจาก...” หรือ “แนะนำให้...” ไม่กล่าวว่าผู้เรียนมีปัญหานั้นอยู่แล้ว
- ไม่กล่าวว่าผู้เรียนได้รับอนุมัติหรือพร้อมทำงานทุกด้านเพียงเพราะผ่านเกณฑ์หลักสูตร
- ไทย/อังกฤษต้องใช้ข้อค้นพบและสถานะเดียวกัน ไม่เติมข้อสรุปใหม่เฉพาะภาษาใดภาษาหนึ่ง

### ตัวอย่างเป้าหมายด้านสำนวน

ตัวอย่างนี้ใช้ข้อมูลสมมติที่สอดคล้องกับภาพที่ผู้ใช้ส่ง ไม่ใช่ผลประเมินที่นำไปบันทึกจริง และตัวเลขในย่อหน้าแรกต้องมาจาก Backend

> **ภาพรวมความพร้อมก่อนสหกิจศึกษา**
>
> จากผลตรวจสอบของระบบ ผู้เรียนถึงเกณฑ์ความพร้อมทั้ง 5 ข้อที่หลักสูตรกำหนดสำหรับภาคเรียนที่เลือก โดยมีเกรดเฉลี่ยรวม 3.53 และเกรดเฉลี่ยในหมวดวิชาเฉพาะ 3.46 สูงกว่าเกณฑ์ขั้นต่ำ 3.00 ขณะที่รายวิชา Seminar ได้รับเกรด A สูงกว่าเกณฑ์ขั้นต่ำ B ผลดังกล่าวสะท้อนว่าผลการเรียนถึงเกณฑ์ตามข้อมูลที่ใช้ตรวจสอบครั้งนี้ การอนุมัติไปสหกิจศึกษายังคงเป็นไปตามกระบวนการของหลักสูตร
>
> **จุดแข็งที่มีหลักฐานรองรับ**
>
> ผลการเรียนโดยรวมและในหมวดวิชาเฉพาะถึงเกณฑ์ที่หลักสูตรกำหนด จึงเป็นข้อมูลประกอบการเตรียมความพร้อมด้านการเรียนก่อนสหกิจศึกษา อย่างไรก็ตาม ผลการเรียนส่วนนี้ควรอ่านร่วมกับคะแนนสมรรถนะและผลงานที่เกี่ยวข้อง เพื่ออธิบายการนำความรู้ไปใช้ได้ชัดเจนขึ้น โดยไม่สรุปความสามารถเฉพาะด้านจากเกรดเพียงอย่างเดียว
>
> **แนวทางเตรียมตัวต่อ**
>
> แม้ผลตรวจจะถึงเกณฑ์แล้ว ผู้เรียนอาจใช้ช่วงเวลาก่อนเริ่มสหกิจเพื่อทบทวนสิ่งที่เรียนและจัดเตรียมผลงานที่เกี่ยวข้อง หากมีโครงงานหรือชิ้นงานจากรายวิชา แนะนำให้ทบทวนบทบาทของตนเอง ขั้นตอนที่ทำ และวิธีจัดการปัญหาที่พบ เพื่อใช้ประกอบการอธิบายประสบการณ์ของตนเองอย่างเป็นรูปธรรม
>
> **ขอบเขตของการประเมิน**
>
> รายงานนี้ใช้รายวิชาและเกรดก่อนภาคเรียนที่เลือก ส่วนกิจกรรมใช้ข้อมูลล่าสุดที่ระบบมี ขณะนี้คะแนนสมรรถนะจากวิชาเสรียังไม่พร้อม และยังไม่มีข้อมูลการเข้าร่วมกิจกรรม จึงยังอธิบายความสามารถจากข้อมูลส่วนดังกล่าวได้จำกัด เมื่อข้อมูลพร้อมแล้วจึงนำมาประกอบรายงานฉบับใหม่ได้

ถ้ามีเกณฑ์ไม่ผ่าน ย่อหน้าแนวทางพัฒนาต้องอธิบายสิ่งที่ขาดจากผลตรวจเดิมและสิ่งที่ทำต่อได้ ถ้ายังไม่มีผลการเรียน ต้องระบุว่ารอข้อมูล ไม่เขียนว่าไม่ผ่าน

## 5. Architecture และสัญญา Output

ใช้กระบวนการเดิม: Snapshot -> Compaction -> Verified Observations -> LLM -> Validator -> Backend Assembler -> ตรวจ Source Hash -> บันทึก -> UI

เพิ่มชั้นประกอบย่อหน้าใน Backend แยกจากการสร้างข้อค้นพบและการเรียก Provider เพื่อให้เปลี่ยนรูปแบบรายงานได้โดยไม่กระทบตัวคำนวณ

### Provider Output ที่เสนอ

LLM คืน JSON ที่มี `paragraphs` แทนรายการการ์ดเดิม แต่ละย่อหน้ามีประโยคที่อ้าง `observation_id` ของ Backend การแยกประโยคเป็นโครงสร้างมีไว้สำหรับตรวจหลักฐาน ส่วน UI รวมประโยคให้เป็นความเรียงหนึ่งย่อหน้า

```json
{
  "paragraphs": [
    {
      "section": "strengths",
      "sentences": [
        {
          "observation_id": "<ID จาก verified_observations>",
          "intent": "explanation",
          "text": {"th": "ข้อความอธิบาย...", "en": "Explanation..."}
        }
      ]
    },
    {
      "section": "development",
      "sentences": [
        {
          "observation_id": "<ID จาก verified_observations>",
          "intent": "advice",
          "text": {"th": "แนะนำให้...", "en": "Consider..."}
        }
      ]
    }
  ]
}
```

ขอบเขตเริ่มต้นสำหรับทดสอบ:

- `section` อนุญาต `strengths`, `development`, `observations`
- ไม่เกิน 4 ย่อหน้าจาก LLM รวมทั้งหมด: strengths ไม่เกิน 2, development ไม่เกิน 1, observations ไม่เกิน 1
- ย่อหน้าหนึ่งมี 1-4 sentence entries; แต่ละข้อความไม่เกิน 240 Unicode characters ต่อภาษา และรวมต่อย่อหน้าไม่เกิน 700 ต่อภาษา
- ยอมรับ `paragraphs: []` เมื่อไม่มีข้อค้นพบที่ LLM อธิบายได้ แต่ต้องมีผลตรวจหรือข้อมูลบางส่วนให้ Backend ประกอบรายงาน; กรณีไม่มีหลักฐานเลยยังใช้สถานะ insufficient data เดิม
- เพิ่มความยาวด้วยหลายประโยคที่สัมพันธ์กัน ไม่เพียงปลดเพดานความยาวจน Output ไม่จำกัด
- strengths/explanation อ้างได้เฉพาะ `strength`; observations/explanation เฉพาะ `neutral`
- development/explanation อ้างได้เฉพาะ `limitation`; development/advice อ้างข้อค้นพบที่มีอยู่ได้ทุก kind เพื่อให้แนะนำการเตรียมตัวได้เมื่อผ่านทุกเกณฑ์
- ID เดิมอ้างซ้ำได้เมื่อเป็นการอธิบายแล้วแนะนำ หรือเชื่อมประโยคในย่อหน้าเดียวกัน แต่ห้ามซ้ำข้อความเดิมเพื่อเพิ่มความยาว
- ไม่ให้ LLM คืนผล readiness, ชื่อหัวข้ออิสระ, `evidence_refs` อิสระ, ตัวเลขใหม่, ค่าคะแนน/เกรดที่คำนวณเอง หรือข้อความ Markdown/HTML

### การประกอบผลที่บันทึก

Backend ประกอบ `AssessmentValidatedOutput` รุ่นใหม่ให้มี `schema_version` และ `narrative` แบ่งเป็น `readiness`, `strengths`, `development`, `observations`, `data_scope`

- ย่อหน้าที่ LLM สร้างเก็บ sentence entries ที่ผ่านการตรวจ พร้อม `evidence_refs` ที่ Backend resolve จาก observation catalog และ provenance เดิม
- readiness/data_scope เป็นข้อความสองภาษาที่สร้างจาก Template ของ Backend พร้อมหลักฐานจากผลตรวจและ Availability ไม่ให้โมเดลเขียนผลผ่าน/ไม่ผ่านใหม่
- readiness อธิบายสถานะรวมอย่างถูกต้องทั้ง met, not met, missing grade และ not configured; เลือกข้อสำคัญมาเล่าและเปิดหลักฐานดูผลทุกข้อได้ ไม่ตัดความหมายว่า “ผ่านทั้งหมด” จากจำนวนบางส่วน
- ตัวเลข ชื่อรายวิชา และเกรดในย่อหน้าความพร้อมใส่ผ่าน Template ของ Backend โดยใช้แหล่งข้อมูลเดิมและกฎการปัดเดิม
- ถ้าจำเป็นต้องแสดงตัวเลขในส่วนวิเคราะห์ ให้ Backend สร้างประโยคข้อเท็จจริงจาก Values แล้วรวมไว้เพียงครั้งเดียว ห้ามพึ่งการตรวจว่าเลขนั้นอยู่ในชุดตัวเลขเพื่อยืนยันว่า LLM ใช้ความหมายถูก
- data_scope บอกแหล่งข้อมูลที่ขาดและเหตุผลจาก reason code รวมเหตุผลซ้ำให้อ่านง่าย โดยเปิดดูรายละเอียดต้นทางได้
- Frontend รับ JSON ที่ Backend ประกอบแล้ว ไม่สร้างผลวิเคราะห์หรือคำนวณคะแนนเพิ่มเอง

## 6. Validation และคุณภาพเนื้อหา

ปรับ Validator เดิม ไม่ตัดการตรวจ ID, provenance, PII, สองภาษา และขนาดข้อมูลออก

1. ตรวจ strict JSON, required fields, enum, จำนวนย่อหน้า/ประโยค, ความยาว และ trailing content
2. ตรวจทุก observation_id ว่ามีจริงใน Snapshot งานนั้น และอยู่ใน section/intent ที่อนุญาต
3. Backend เป็นผู้ resolve EvidenceRefs และชื่อข้อค้นพบ ไม่รับหลักฐานที่โมเดลสร้างเอง
4. ข้อความ LLM ไม่กล่าวอ้างตัวเลขหรือเกรดใหม่ ตัวเลขที่ต้องแสดงในรายงานใช้ Template ของ Backend ตามข้อ 5
5. ตรวจข้อความขัดผลตรวจอย่างชัดเจน การอนุมัติสิทธิ์ ชื่ออาชีพ และการอ้างความสามารถจากข้อมูลขาดด้วยกรณีทดสอบและการประเมินโมเดล
6. คงชื่อ/ข้อความต้นทางเป็น untrusted data; ถ้าต้องส่ง label เพิ่ม ให้ส่งผ่านข้อมูลที่ sanitize แล้วและทดสอบ prompt injection
7. ถ้าความหมายของสองภาษาไม่ตรงกันหรือมีข้อสรุปเกินหลักฐานในการประเมินตัวอย่างจริง ถือว่าไม่ผ่าน Release Gate

การตรวจ JSON, keyword และ ID ไม่สามารถพิสูจน์ความถูกต้องเชิงความหมายทุกประโยคได้ ต้องประเมินรายงานจริงประกอบ และไม่ประกาศว่าระบบป้องกัน hallucination ได้ทั้งหมด

## 7. Context, Output Tokens และเวลาในการสร้าง

รายงานความเรียงสองภาษายาวกว่า Output เดิม ต้องประเมินทั้งความครบและความเร็วบนเครื่อง RAM 16 GB / VRAM 4 GB

- คง Compaction และ prompt จาก verified observations ไม่ส่ง Snapshot เต็มหรือ catalogue อาชีพเข้าโมเดล
- ใช้ `num_predict` สอดคล้องกับ `LEARNER_ASSESSMENT_OUTPUT_RESERVE_TOKENS` และคำนวณ Input Budget ใหม่ทุกครั้ง
- ทดลองค่าปัจจุบันจริงเป็น baseline และ Context 12288 / Output Reserve 3072 / Safety Margin 128 เป็น candidate; ถ้า Output ยังถูกตัด ทดลอง reserve 4096 โดยตรวจงบ Input ใหม่และวัดหน่วยความจำ
- 12288 คือค่าทดลอง ไม่แก้ค่าเริ่มต้นของทุก Environment โดยอัตโนมัติ และไม่ยืนยันว่าจะเร็วหรือใช้ VRAM พอจนกว่าจะวัดจริง
- หาก reserve ใหม่ไม่พอกับ Context ที่ตั้งไว้ ต้องแจ้ง config/context error ก่อนเรียก Provider ไม่ตัดข้อมูลสำคัญเงียบ ๆ
- ถ้าโมเดลเขียนยาวจนถูกตัด ให้ลดจำนวนประโยค/ย่อหน้า หรือปรับ reserve ตามผลทดลอง ห้ามบันทึก JSON ครึ่งฉบับ
- วัด prompt/output token จริง, TTFT เมื่อ Provider ส่งได้, เวลารวม, RAM/VRAM, truncation และจำนวน Retry
- คง Streaming ที่ใช้รายงานความคืบหน้า โดยไม่แสดงข้อความที่ยังไม่ตรวจ; แสดงฉบับสำเร็จเมื่อ Validate และบันทึกแล้ว
- คง progress phases, ตรวจ Heartbeat/Lease และ fallback ตรวจ ownership ของ no-op UpdateProgress ที่แก้แล้ว
- ค่า timeout ต้องสอดคล้องผลทดสอบและ Attempt Timeout เดิม ไม่เพิ่มโดยไม่มีขอบเขต

## 8. Database, API และการเปลี่ยนผ่าน

ไม่ต้อง Migration สำหรับรุ่นนี้ เนื่องจากรายงานเป็น JSON และมีคอลัมน์ Pipeline/Prompt/Schema Version อยู่แล้ว

- ใช้ `ai_learner_reports`, `ai_report_jobs`, Source Snapshot และ API เดิม
- เปลี่ยนรุ่น Pipeline เป็น `learner-assessment-v1.1.0`, Prompt เป็น `learner-assessment-prompt-v1.1.0`, Schema เป็น `learner-assessment-output-v1.1.0`
- ใช้รุ่น Compaction เดิมถ้าไม่ได้เปลี่ยนกติกาย่อข้อมูล; หากเปลี่ยนต้องเพิ่มรุ่นและทดสอบ provenance ด้วย
- Version และ Generation Config ต้องเข้า source hash ตามระบบเดิม ทำให้รายงาน v1.0 ล้าสมัยและสร้างใหม่ตาม Flow ปัจจุบัน
- ไม่แปลงข้อความ v1.0 มาเรียงแล้วอ้างว่าเป็นผล LLM v1.1 ที่ผ่านการตรวจ
- Worker ต้องปฏิเสธ Snapshot รุ่นเก่าด้วยสถานะที่รู้จัก และระบบเปิดรายงานสามารถสร้างงานรุ่นใหม่ได้ ไม่ปล่อยให้วนใช้ active job รุ่นเก่า
- ตรวจ source hash อีกครั้งก่อนบันทึก ป้องกันงานเดิมที่สร้างเสร็จช้ากว่าเขียนทับรายงานรุ่นใหม่
- Deploy API/Worker/Frontend รุ่นที่รองรับ Schema เดียวกันร่วมกัน และรักษาข้อมูลเดิมไว้สำหรับ rollback

## 11. Acceptance Criteria และการทดสอบรวม

### ความถูกต้อง

- ผ่านทั้งหมด, ไม่ผ่านบางข้อ, รอเกรด, ไม่มีเกณฑ์, หลักฐานบางส่วน และไม่มีหลักฐาน ให้ข้อความตรงกับสถานะระบบ
- ตัวเลข เกรด เป้าหมาย และจุดตัดเวลาในเนื้อหาจาก Backend ถูกต้อง และไม่อ้างข้อมูลหลังเทอมเป้าหมาย
- ไม่มีข้อสรุปความสามารถหรือบุคลิกจากคะแนนสะสม/ชื่อวิชาเพียงอย่างเดียว
- คำแนะนำเมื่อผ่านครบเป็นการเตรียมตัว ไม่อ้างว่าพบข้อบกพร่อง
- หลักฐานทุกย่อหน้า resolve ได้จาก Snapshot ที่ใช้สร้าง และความหมายสองภาษาตรงกัน
- ข้อมูลใหม่ระหว่างสร้าง, หลายแท็บ, cooldown, Snapshot รุ่นเก่า และ Lease ที่สูญเสียยังจัดการตามระบบเดิม

### คุณภาพรายงานและประสิทธิภาพ

- ใช้ fixture อย่างน้อย 6 กลุ่ม: ผ่านครบ, ไม่ผ่านบางข้อ, รอเกรด/ไม่มีเกณฑ์, กิจกรรมพร้อม, คะแนนบางส่วนไม่พร้อม, หลักฐานมากพร้อมข้อความต้นทางที่พยายามสั่งโมเดล
- ใช้ข้อมูลสังเคราะห์ ไม่มี PII จริง และตรวจด้วย Ollama/model digest ที่จะใช้งานอย่างน้อย 2 รอบต่อกลุ่ม
- ผลสำเร็จต้องเป็นความเรียงเชื่อมประโยค อ่านรู้เรื่อง ไม่ใช่การนำ Fact/Explanation เดิมมาต่อโดยซ้ำเนื้อหา
- ไม่ต้องเล่าทุก observation ในรายงาน แต่ผลตรวจที่ไม่ผ่าน/รอข้อมูลต้องเข้าถึงได้จาก readiness และหลักฐานรายเกณฑ์ครบ
- เกณฑ์ hard gate: ไม่มีการกลับผล readiness, ไม่มีหลักฐานปลอม, ไม่มีการอนุมัติสิทธิ์หรือแนะนำอาชีพ, ไม่มีความต่างสาระสำคัญระหว่างสองภาษาในตัวอย่างที่ตรวจ
- รอบทดสอบต้องไม่มี final job failure จาก truncation ใน fixture ที่กำหนด บันทึกจำนวน Retry และ first-attempt success เพื่อไม่ซ่อนปัญหาประสิทธิภาพ
- วัดเวลาสร้างให้สัมพันธ์กับ timeout ที่ตั้งจริง ถ้าช้าจนใช้ไม่ได้ ให้ลดความยาว/งบตามผลทดลองก่อนยืนยัน Release Gate
- ทดสอบ Browser ไทย/อังกฤษ, Light/Dark, Desktop/Mobile, Keyboard, หลักฐาน, สร้างใหม่ และ Loading/Retry ด้วย screenshot ตรวจการล้นและการตัดข้อความ

คำสั่งตรวจ: `go test ./...`, Frontend tests ที่เกี่ยวข้อง, ESLint เฉพาะไฟล์เปลี่ยน, `npm.cmd run build`, `git diff --check` และ synthetic model evaluation ตามวิธีใน `docs/context/learner-llm-report/operations.md` ที่อัปเดตแล้ว

## 12. สิ่งที่ไม่อยู่ในงานนี้
