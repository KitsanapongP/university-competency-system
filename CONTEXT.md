# Project Context: University Competency System

## Session Attendance And Score Rules
* **Session Setup Finalization:** `is_setup_finalized = 1` locks session configuration (time, location, assignments, and competency mapping). It does not block the lifecycle transition from `scheduled` to `completed` or `cancelled`.
* **Score Finalization:** `scores_finalized_at` and `scores_finalized_by` lock attendance-derived scores and competency results after completion. Finalization requires setup lock, recorded attendance for every approved participant, and complete scores for all eligible participant-competency pairs.
* **Attendance Source Of Truth:** `att_session_attendances` stores actual participation: `present`, `late`, `absent`, and `excused`. Registration is approval/admission only; APIs do not write legacy `checked_in` or `no_show` statuses.
* **Score Correction:** An explicit reason opens one active `score_session_correction_logs` row per session. It sets `scores_recalculation_required = 1`, unlocks only attendance and session score records, then requires score finalization again to recompute and lock results.
* **Session Score Roll-Up:** Session competency results are recomputed from source rows and combined with course competency scores for the learner's one active enrollment in the activity faculty. The system never incrementally adds a prior session result.

## Project Overview (โปรเจคนี้ทำอะไร และทำเพื่ออะไร)
**University Competency System** เป็นระบบบริหารจัดการและประเมิน "สมรรถนะ (Competency)" ของนักศึกษาระดับมหาวิทยาลัย 
*   **เป้าหมายหลัก:** เพื่อติดตามการสะสมทักษะของนักศึกษาตลอดการเรียนในหลักสูตร โดยอิงจากการได้มาซึ่งคะแนนสมรรถนะผ่านแต่ละรายวิชาที่ลงทะเบียนเรียน
*   **จุดเด่น:** ระบบถูกออกแบบให้รองรับการตั้งเป้าหมายระดับหลักสูตร (Curriculum Requirements) และการกำหนดค่าน้ำหนักสมรรถนะรายวิชาที่ยืดหยุ่นผ่านระบบ Template ซึ่งทำให้หลักสูตรเดียวกันสามารถมีเกณฑ์การประเมินที่ต่างกันตาม "ปีการศึกษาที่เข้าเรียน (Cohort)" ได้ 
*   **การแสดงผล:** คะแนนสุดท้าย (Final Score) ที่ผ่านการคูณน้ำหนักและสะสมมา จะถูกนำไปพล็อตเป็น **Radar Chart** เพื่อให้นักศึกษาได้เห็นจุดเด่นและจุดที่ต้องพัฒนาของตนเองเมื่อเทียบกับเป้าหมายที่หลักสูตรตั้งไว้

## System Scope (ขอบเขตของระบบ)
*   ระบบใช้สำหรับติดตามการเข้าร่วมกิจกรรมของผู้เรียน (Attendance / Participation)
*   กิจกรรมแต่ละรายการสามารถกำหนดได้ว่าจะให้คะแนนสมรรถนะ (Competency) ด้านใดบ้าง
*   เมื่อผู้เรียนเข้าร่วมกิจกรรม ระบบจะบันทึกและสะสมข้อมูลสมรรถนะ
*   แสดงผลสมรรถนะของผู้เรียนในรูปแบบ Radar Chart เพื่อให้เห็นภาพรวมการพัฒนาของตนเอง

## Organizational Structure (โครงสร้างระดับองค์กร)
*   โครงสร้างลำดับชั้น: University -> Faculty -> Department -> Major -> Curriculum
*   การมองเห็นกิจกรรมอ้างอิงตาม **Faculty** เป็นหลัก โดยแต่ละ Faculty จะมีกิจกรรมที่แตกต่างกัน
*   ผู้ใช้ภายใน Faculty เดียวกันจะเห็นชุดกิจกรรมเดียวกัน
*   การจัดการความสัมพันธ์ระหว่าง Faculty และกิจกรรมดำเนินการโดยเจ้าหน้าที่ฝ่ายพัฒนาการนักศึกษา

## Target Audience / User Roles (บทบาทผู้ใช้งานเป้าหมาย)
ระบบนี้ถูกออกแบบมาเพื่อรองรับผู้ใช้งาน 5 กลุ่มหลัก ได้แก่:

1. **ผู้เรียน (Learner)**
   * เช็คชื่อเข้าร่วมกิจกรรม/รายวิชา
   * ประเมินกิจกรรมว่ามีประโยชน์มากน้อยเพียงใด
   * ดูผลการประเมินสมรรถนะและพัฒนาการของตนเองผ่าน Radar Chart

2. **อาจารย์ (Lecturer)**
   * เช็คชื่อผู้เรียน
   * ประเมินสมรรถนะของผู้เรียนจากกิจกรรมและรายวิชา

3. **เจ้าหน้าที่ฝ่ายพัฒนาการนักศึกษา (Student Development Officer)**
   * นำเข้าข้อมูลนักศึกษา
   * จัดการกิจกรรมและรายวิชาต่างๆ
   * เพิ่ม แก้ไข และจัดการสมรรถนะ (Competency)
   * กำหนดความสัมพันธ์ระหว่างกิจกรรม/รายวิชากับสมรรถนะ (รวมถึงการจัดการ Template)

4. **ผู้ดูแลระบบ (Admin)**
   * จัดการและตั้งค่าระบบได้ทุกส่วน
   * จัดการ role, permission และการตั้งค่าพื้นฐานของระบบ

5. **ผู้บริหารคณะ (Dean)**
   * ดูข้อมูลภาพรวม (Dashboard) ของระบบทั้งหมด
   * ส่งออกข้อมูลในรูปแบบรายงาน (Report) เพื่อการบริหารจัดการ

## Core Business Logic (ตรรกะทางธุรกิจหลักของระบบ)
*   **การแยก Goal และ Execution ออกจากกัน:** ระบบเก็บ "เป้าหมายหลักสูตร" ไว้ที่ `comp_curriculum_requirements` (เสมือนเส้นชัย) และเก็บ "น้ำหนักของรายวิชา/กิจกรรม" ไว้ใน `comp_template_items` (เสมือนวิธีการได้มาซึ่งคะแนน)
*   **การจัดการตามปีเข้าศึกษา (Cohort-based Strategy):** ระบบถูกออกแบบให้อ้างอิงตาม "ปีที่เข้าศึกษา (`cohort_year_be`)" ทำให้หลักสูตรเดียวกันสามารถปรับเปลี่ยนเป้าหมายสมรรถนะ หรือแก้ไขน้ำหนักรายวิชาของเด็กปี 66 ได้ โดยไม่ส่งผลกระทบย้อนหลังกับเด็กปี 65
*   **การคำนวณคะแนนและการรีเกรด (Retake Handling):** การคำนวณคะแนนสะสมที่จะนำไปพล็อตลง Radar Chart จะนับเฉพาะรายวิชาที่สอบผ่านและได้เกรดดีที่สุดเท่านั้น (`is_best_grade = 1`) เพื่อป้องกันปัญหานักศึกษาเรียนซ้ำ (Retake) แล้วคะแนนสมรรถนะเฟ้อผิดปกติ

## Module Breakdown (โครงสร้างโมดูลหลัก)
*   **`/curriculum-management`**: โมดูลสำหรับจัดการโครงสร้างหลักสูตร, หมวดวิชา, และการดึงรายวิชาเข้ามาผูกในหลักสูตร
*   **`/template-management`**: โมดูลสำหรับผูกความสัมพันธ์ว่ารายวิชาใด แจกสมรรถนะใดบ้าง และแต่ละสมรรถนะมีน้ำหนักเท่าไหร่
*   การวาง Routing ในฝั่ง Frontend (Next.js) จะแบ่งตามสิทธิ์ผู้ใช้งาน เช่น หน้าจอของเจ้าหน้าที่จะถูกจัดกลุ่มไว้ใต้โฟลเดอร์ `app/(officer)/...`

## Key Terminology (คำศัพท์เฉพาะในโปรเจค)
*   **Curriculum (หลักสูตร):** โครงสร้างวิชาเรียน เช่น วท.บ. วิทยาการคอมพิวเตอร์
*   **Course (รายวิชา):** รายวิชาของหลักสูตรหนึ่ง ๆ ไม่ใช่รายวิชากลางข้ามหลักสูตร รหัสวิชา ชื่อวิชา คำอธิบาย และหน่วยกิตเป็นข้อมูลของ Course นั้นในบริบทของ Curriculum ที่สร้างมันขึ้นมา
*   **Course Ownership:** Each Course belongs to exactly one Curriculum. Courses with the same code in different Curricula are separate Course records and can have different names, descriptions, and credits.
*   **Course Code Uniqueness:** Course codes are unique only within the same Curriculum among non-deleted Courses. Different Curricula can have Courses with the same code. A soft-deleted Draft Course does not block reuse of its code in the same Curriculum.
*   **Course Scope Derivation:** A Course's faculty and degree context comes from its Curriculum and Major, not from independent Course fields.
*   **Curriculum Course (รายวิชาในหลักสูตร):** ความสัมพันธ์ที่จัด Course เข้าไปอยู่ภายใต้หมวดวิชาของ Curriculum เป็นตำแหน่ง/การจัดกลุ่มของ Course ภายในโครงสร้างหลักสูตร ใช้เก็บข้อมูลการจัดวาง เช่น หมวดวิชา ลำดับแสดงผล required/elective active/locked ไม่ใช่เจ้าของข้อมูลชื่อ คำอธิบาย หรือหน่วยกิตของรายวิชา
*   **Curriculum Course Detail Edit:** Editing a Course's Thai name, English name, or description does not change its Template mapping target. Editing a Course code is allowed when it remains unique within the Curriculum; connected Templates and history display the new code. Editing Course credits is allowed, but connected Templates are shown as affected because Template credit summaries may change. These detail edits do not require score recalculation under the current scoring rules.
*   **Curriculum Course Placement Edit:** Moving a Course to another Category is a Curriculum structure edit. It follows the same lock and impact-confirmation rules as other Curriculum structure edits, because connected Templates show the Course under the updated Category placement.
*   **Course Edit Boundary:** Course details and Curriculum Course placement are separate edit concepts. Course detail edits change the Course itself, while Curriculum Course placement edits change where that Course appears in the Curriculum structure.
*   **Template Additional Course (รายวิชาเพิ่มเติมเฉพาะรุ่น):** รายวิชาที่เพิ่มใน Template สำหรับ Cohort ใด Cohort หนึ่งโดยเฉพาะ เช่น วิชาพิเศษที่เปิดเฉพาะปีนั้น รายวิชานี้มีรหัสวิชา ชื่อไทย ชื่ออังกฤษ หน่วยกิต คำอธิบาย และหมวดวิชาที่เลือกใน Template Management หมวดวิชาที่เลือกอาจเป็นหมวดจาก Curriculum หรือ Template Additional Category รายวิชานี้ไม่ใช่ส่วนหนึ่งของ Curriculum structure ไม่กระทบ Template อื่นที่ใช้ Curriculum เดียวกัน และไม่นับเป็น Total Credits ของ Curriculum
*   **Template Additional Category (หมวดวิชาเพิ่มเติมเฉพาะรุ่น):** หมวดวิชาที่สร้างใน Template Management สำหรับจัดวาง Template Additional Courses ใน Cohort ใด Cohort หนึ่งโดยเฉพาะ หมวดนี้ไม่ใช่ส่วนหนึ่งของ Curriculum structure และไม่กระทบ Template อื่นที่ใช้ Curriculum เดียวกัน
*   **Template Additional Category Deletion:** When a Template Additional Category is removed from a Template, all Template Additional Courses inside that category are removed with it after a clear user warning and confirmation, including their Course-Competency mappings and weights.
*   **Template Category Name Uniqueness:** ภายใน Template เดียวกัน ห้ามชื่อหมวดวิชาซ้ำกัน ไม่ว่าจะเป็นหมวดที่มาจาก Curriculum หรือ Template Additional Category เพื่อป้องกันการสร้างหมวดที่ผู้ใช้เข้าใจผิดว่าเป็นหมวดเดียวกัน ชื่อหมวดสามารถซ้ำกันได้ข้าม Template หรือข้าม Cohort
*   **Template Course Code Uniqueness:** ภายใน Template เดียวกัน ห้าม Template Additional Course ใช้รหัสวิชาซ้ำกับ Curriculum Course หรือ Template Additional Course อื่น เพื่อป้องกันการเพิ่มวิชาที่มีอยู่ในหลักสูตรแล้วโดยไม่ได้ตั้งใจ รหัสวิชาสามารถซ้ำกันได้ข้าม Template หรือข้าม Cohort
*   **Template Additional Course Deletion:** When a Template Additional Course is removed from a Template, its Course-Competency mappings and weights are removed with it after a user warning and confirmation, because they no longer have meaning in that Template's scoring structure.
*   **Curriculum Duplication (การคัดลอกหลักสูตร):** การสร้างหลักสูตรใหม่จากหลักสูตรเดิมเพื่อเป็นจุดเริ่มต้นของหลักสูตรรุ่นใหม่ เช่น คัดลอก CS65 ไปเป็น CS70 แล้วแก้โครงสร้างวิชา หมวดวิชา metadata หน่วยกิต และคำอธิบายตามหลักสูตรใหม่ โดยคัดลอกเฉพาะโครงสร้างหลักสูตร หมวดวิชา และความสัมพันธ์รายวิชาในหลักสูตร ไม่คัดลอก Template หรือการ mapping สมรรถนะ
*   **Duplicated Curriculum Status:** A duplicated Curriculum always starts as Draft, regardless of the source Curriculum status.
*   **Duplicated Course Records:** Duplicating a Curriculum creates new Course records for the target Curriculum. The duplicated Curriculum never reuses source Course IDs, so course names, descriptions, and credits can change without affecting the source Curriculum.
*   **Faculty Scope (ขอบเขตคณะ):** เจ้าหน้าที่ทำงานภายใต้คณะของตนเอง หลักสูตร สาขาวิชา และรายวิชาที่สร้างผ่าน Curriculum Management ต้องอยู่ภายใต้คณะเดียวกับผู้ใช้งาน ยกเว้นผู้ดูแลระบบที่มีสิทธิ์ข้ามคณะ
*   **Major Selection Scope:** Student Development Officers can select only majors that belong to their own Faculty Scope when creating or managing a Curriculum. Admin users can work across faculties by selecting a Faculty first, then selecting a Major within that Faculty.
*   **Faculty Selection in Curriculum Management:** A Student Development Officer's faculty is contextual information, not a selectable input, during Curriculum creation. Admin users select a Faculty first, then select a Major within that Faculty.
*   **Missing Faculty Scope:** A Student Development Officer without a Faculty Scope cannot create or manage Curricula until an Admin assigns the user to a Faculty. If the user's Faculty has no active Majors, Curriculum creation is unavailable until a Major exists in that Faculty.
*   **Major Display Label:** Major selection presents a human-readable label made from the Major code, Thai name, and degree level. The hidden identifier sent to backend APIs remains the Major ID.
*   **Curriculum Lifecycle Status:** A Curriculum can be Draft, Active, or Inactive. New Curricula start as Draft. Draft Curricula are not ready for use and remain editable, including their Major. Active Curricula are ready for use and cannot change Major. Inactive Curricula were previously ready for use but are temporarily disabled and can be made Active again. "Retired" is not part of the current Curriculum lifecycle; if permanent retirement is needed later, it must be defined as a separate lifecycle state.
*   **Curriculum Status Labels:** Draft is shown as "ฉบับร่าง", Active as "พร้อมใช้งาน", and Inactive as "ปิดใช้งาน" in the user interface.
*   **Curriculum Activation:** A Draft or Inactive Curriculum can become Active only after it has the minimum usable structure: a code, a Thai name, a Major, at least one non-deleted category, and at least one non-deleted Curriculum Course placed in a category of that Curriculum. Every current Course in the Curriculum structure must have a code, a Thai name, and non-negative credits. Course codes must be unique within the Curriculum among non-deleted Courses. Required-credit totals are not activation blockers in the current requirement.
*   **Curriculum Deactivation:** An Active Curriculum cannot become Inactive while it has any Active Templates connected to it. All connected Templates must be inactive before the Curriculum can be deactivated.
*   **Curriculum-Template Status Dependency:** An Active Template requires its connected Curriculum to be Active. Inactive Templates cannot become Active while their connected Curriculum is Inactive.
*   **Curriculum Status Transitions:** Curriculum status can transition from Draft to Active, Active to Inactive, and Inactive to Active. Active or Inactive Curricula do not return to Draft, and Draft Curricula do not become Inactive. Inactive Curricula can become Active again only when the Curriculum structure is valid and connected Templates have no activation blockers such as required recalculation.
*   **Curriculum Status Permission:** Student Development Officers can change the status of Curricula within their Faculty Scope. Admin users can change Curriculum status across faculties, but cannot bypass Curriculum lifecycle rules.
*   **Curriculum Major Edit Rule:** A Curriculum's Major can be changed only while the Curriculum is Draft. Active and Inactive Curricula keep their Major fixed.
*   **Curriculum Structure Edit Rule:** Curriculum categories, Curriculum Courses, and Course details such as names, descriptions, and credits can be edited while the Curriculum is Draft, Active, or Inactive. Connected Templates and existing learner scores do not block these configuration changes during development. Destructive category and course actions still require their existing impact confirmations.
*   **Curriculum Category Edit:** A Curriculum Category can be edited for metadata such as code, Thai name, English name, required credits, and display order. A Curriculum Category can also be moved under another Category in the same Curriculum, so long as the move keeps a valid category tree.
*   **Curriculum Category Code:** A Category code is an editable user-facing identifier, separate from `display_order`. The system suggests the next numeric code when a Category is created, but users may keep gaps such as `1` and `3`. A code contains one to four numeric levels separated by dots and is unique among non-deleted Categories in one Curriculum. Renaming a parent code cascades its existing prefix to descendants in the same subtree, while moving or deleting a Category never renumbers other codes.
*   **Curriculum Category Move:** A Curriculum Category can move only within the same Curriculum. A Category can move to the top level, but cannot move under itself or under any of its descendants. Moving a Category moves its subcategory tree and contained Courses with it. Connected Templates that show live Curriculum Categories reflect the new Category placement. Moving a Category does not automatically renumber Category codes.
*   **Curriculum Category Depth:** Curriculum Categories can be nested to a maximum of four levels. Existing deeper category trees remain visible so officers can correct them, but new or moved categories cannot make a branch deeper than four levels.
*   **Curriculum Course Placement Rule:** A Curriculum Course is placed only in a leaf Curriculum Category. A Category containing Courses cannot gain child Categories, and Courses in legacy non-leaf Categories must be moved to a leaf Category before their placement is changed.
*   **Curriculum Category Deletion Impact:** When a Curriculum Category is deleted, users are warned about every affected subcategory, Curriculum Course, Template Additional Course, Course-Competency mapping, and weight before confirmation. Deleting a parent category deletes its subcategory tree. Courses placed under the deleted category tree are moved to another category in this order: the previous sibling category at the same hierarchy level, the next sibling category at the same hierarchy level, then the nearest parent category if no sibling exists. The move target is calculated from the Category being deleted, not separately from each descendant Category in the deleted subtree. If no parent category exists, the affected Courses are soft-removed from that Curriculum or Template course structure rather than hard-deleted. Existing Course-Competency mappings and weights stay with moved Courses. For soft-removed Curriculum Courses, normal Template mappings and weights are soft-removed when no active placement of the Course remains in the owning Curriculum and are excluded from future duplication and scoring.
*   **Curriculum Category Delete Confirmation:** Deleting a Curriculum Category is a two-step operation. Users first review a delete preview showing affected subcategories, moved Courses, soft-removed Courses, and affected Templates. The actual delete proceeds only after explicit confirmation.
*   **Curriculum Course Soft Removal:** When a Category deletion has no destination Category for affected Courses, the Curriculum Course placement is soft-removed from the current structure. The Course record itself is not deleted at that point.
*   **Curriculum Course Deletion:** Deleting a Course from the Curriculum structure means soft-removing its Curriculum Course placement from the current structure. The Course record itself remains for history and possible restoration. When no active placement remains in the owning Curriculum, normal Template mappings and weights for that Course are soft-removed in the same transaction and are not restored automatically.
*   **Curriculum Course Addition:** Adding a Course to a Curriculum creates a new Course record for that Curriculum. The system does not reuse a Course from another Curriculum or a central Course master.
*   **Curriculum Structure Excel Import:** Excel structure import is add-only. It can reuse an existing Category only when its code, Thai name, and parent path match, otherwise it creates the Category and adds new Courses. The imported file specifies Category code and Thai name for levels 1 through 4, followed by Course code, Thai name, optional English name, and credits. The entire import is blocked and rolled back when any row has a hierarchy gap, Category conflict, duplicate Course code, invalid credits, or a Course placed in a non-leaf Category. Import follows the same Curriculum scope, lifecycle lock, and impact-confirmation rules as other structure edits.
*   **Removed Courses:** Courses soft-removed from a Curriculum or Template course structure are shown separately in a History or Removed Courses section when they have historical meaning. They are not shown in the current course list and are not treated as current mapping requirements. Removed Courses can be restored only when there is no real usage yet, or when the relevant Template or Curriculum is inactive and the user confirms the restoration. If the original category no longer exists, the user must choose the destination category during restoration. A removed Curriculum Course does not automatically restore its old Template mappings or weights; the user must configure them again. Restoring a Course that affects existing scores requires recalculation.
*   **Inactive Curriculum Edit Rule:** An Inactive Curriculum keeps its Major fixed, but its structure can be edited after the user is warned which Templates may be affected. Student Development Officers use this warning to decide whether to proceed with the edit, because the change may require Template review or score recalculation before related Templates can be made Active again.
*   **Curriculum Edit Impact Confirmation:** Structure edits to an Inactive Curriculum require explicit user confirmation after the affected Templates are shown. The edit does not proceed until the user acknowledges the impact.
*   **Affected Templates:** Affected Templates are all non-deleted Templates connected to the Curriculum being changed. They are shown with different severity levels so users can distinguish Draft configuration impact, Inactive Template review impact, Active Template locking impact, and Templates with real scoring usage that may require recalculation.
*   **Curriculum Deletion:** A Curriculum can be deleted only when it is Draft or when it has no connected Templates, and only if it has never had real usage through a Template Assignment. Connected Templates in any non-deleted status count as a dependency that prevents deletion. Curricula with real usage are not deleted; they are made Inactive instead.
*   **Soft Deletion:** Deleting Curricula or Templates from the user interface means soft deletion. Deleted records are hidden from normal lists but remain available for historical integrity.
*   **Curriculum Code Generation:** New Curricula receive a system-generated code in the format `{faculty_code}-{major_code}-{effective_year_be}-{sequence}`. The Faculty and Major codes come from their master records, while the sequence starts at `01` for each Major and effective year. The generator considers soft-deleted Curricula as used sequence values, so it never reuses a generated code.
*   **Curriculum Code Uniqueness:** A Curriculum code is unique within the same Major among non-deleted Curricula. A soft-deleted Draft Curriculum does not block manual reuse where a legacy or duplicate workflow explicitly supplies a code.
*   **Curriculum Effective Year Reuse:** A Major can have multiple non-deleted Curricula in the same effective year. Effective year is metadata for filtering and cohort alignment, not the unique identity of a Curriculum.
*   **Curriculum Thai Name Uniqueness:** A Curriculum Thai name is unique within the same Major and effective year among non-deleted Curricula. This prevents Student Development Officers from accidentally creating the same Curriculum twice in the same Major/year.
*   **Curriculum Duplicate Detection:** Duplicate Curriculum checks consider only non-deleted Curricula. Soft-deleted Draft Curricula do not block reuse of Curriculum code or Thai name.
*   **Curriculum Metadata Ownership:** Curriculum code, Thai name, English name, effective year, and Major are owned by the Curriculum. Faculty and degree level are derived from the selected Major and are managed through Major Management.
*   **Curriculum Metadata Edit Rule:** Curriculum metadata can be edited while the Curriculum is Draft, Active, or Inactive. The Major can be changed only while the Curriculum is Draft. An Admin may move a Draft Curriculum across Faculties; a Student Development Officer can select only a Major inside their own Faculty.
*   **Total Credits (หน่วยกิตรวมของหลักสูตร):** ค่าคำนวณจาก Curriculum Course ทั้งหมดใน Curriculum โดยนับรายวิชาเดียวกันเพียงครั้งเดียว และนับเฉพาะความสัมพันธ์หลักสูตร-รายวิชาที่ยังใช้งานกับรายวิชาที่ยังไม่ถูกลบ ไม่รวม Template Additional Courses ไม่ใช่ข้อมูลที่เก็บถาวรใน Curriculum และไม่ใช่หน่วยกิตขั้นต่ำที่นักศึกษาต้องเรียนให้ครบตาม requirement ของหลักสูตร
*   **Template Credit Summary:** ภาพรวมหน่วยกิตของ Template สำหรับ Cohort หนึ่ง แสดงหน่วยกิตจาก Curriculum, หน่วยกิตจาก Template Additional Courses, และผลรวมของทั้งสองส่วนเพื่อใช้ตรวจสอบภาระรายวิชาที่ถูกนำไปประเมินในรุ่นนั้น
*   **Cohort (รุ่น):** กลุ่มนักศึกษาที่เข้าเรียนในปีการศึกษาเดียวกัน ใน Requirement ปัจจุบัน Cohort ระบุด้วยปีเข้าเรียนเท่านั้น (`cohort_year_be`) และยังไม่แยก track, รอบรับเข้า, หรือกลุ่มพิเศษเป็น entity แยก
*   **Competency (สมรรถนะ):** ทักษะที่ต้องการประเมิน เช่น การสื่อสาร, การคิดเชิงวิพากษ์, ทักษะดิจิทัล
*   **Competency Master:** Competency เป็น global master ของระบบ ไม่ได้แยกตาม Faculty ใน Requirement ปัจจุบัน
*   **Competency Edit Rule:** Competency master ที่ถูกใช้ใน Template ยังแก้รหัส ชื่อ และคำอธิบายได้ เพราะความสัมพันธ์อ้างอิงด้วย `competency_id` ไม่ใช่ชื่อหรือรหัส แต่ยังลบไม่ได้จนกว่าจะไม่มี Template ใช้อยู่ เพื่อไม่ให้ mapping และ weight สูญหาย.
*   **Competency Deletion:** การลบ Competency เป็น soft deletion. Deleted Competencies ถูกซ่อนจากรายการใช้งานปกติ แต่ยังคงอยู่เพื่อ historical integrity
*   **Competency Code Reuse:** Competency code ต้องไม่ซ้ำในกลุ่ม Competency ที่ยังไม่ถูกลบ แต่ soft-deleted Competency ไม่ block การสร้าง code เดิมใหม่
*   **Activity:** กิจกรรมหลักระดับคณะที่ฝ่ายพัฒนานักศึกษาจัดการ เป็น parent entity สำหรับรอบกิจกรรมจริง กิจกรรมใน Requirement ปัจจุบันเป็น `faculty_only` และมองเห็นตาม Faculty เป็นหลัก
*   **Activity Session:** รอบจัดกิจกรรมจริงภายใต้ Activity ใช้เก็บวันเวลา สถานที่ ความจุ เงื่อนไขการลงทะเบียน วิธีให้คะแนน และสถานะการ finalize
*   **Session Assignment:** ผู้รับผิดชอบรอบกิจกรรมจริงใน `act_session_assignments` เช่น lecturer, officer, assistant, supervisor พร้อมสิทธิ์เช็กชื่อ ให้คะแนน หรือ finalize ในรอบนั้น การผูกผู้รับผิดชอบทำที่ Session ไม่ใช่ Activity parent
*   **Session Competency Mapping:** Competency ที่รอบกิจกรรมนั้นให้ใน `act_session_competencies` พร้อม `max_percent` ของแต่ละ Competency สำหรับ Prototype ต้องมี mapping อย่างน้อย 1 รายการ และผลรวม `max_percent` ต้องเท่ากับ 100 ก่อน finalize
*   **Session Finalization:** การ lock setup ของ Activity Session (`is_finalized = 1`) หลัง finalize แล้วห้ามแก้ข้อมูลรอบกิจกรรม ผู้รับผิดชอบ Competency mapping สถานะ และห้ามลบ Session ใน Prototype
*   **Activity Lecturer/Speaker Assignment:** อาจารย์ วิทยากร หรือผู้ประเมินถูกผูกกับ Activity Session ไม่ใช่ Activity parent เพื่อให้สิทธิ์ประเมินและบันทึกข้อมูลสอดคล้องกับรอบกิจกรรมจริง
*   **Activity Lifecycle Status:** Activity เริ่มเป็น Draft, เปลี่ยนเป็น Published เมื่อพร้อมใช้งาน, และเปลี่ยนเป็น Closed เมื่อกิจกรรมนั้นจบวงจรแล้ว Closed หรือ Cancelled Activity เป็นประวัติและไม่ถูกแก้ไขในงานจัดการกิจกรรมรอบปกติ
*   **Activity Open Duplicate Rule:** ภายใน Faculty เดียวกัน ห้ามมี Activity ที่ยัง Draft หรือ Published อยู่โดยใช้รหัสกิจกรรมและชื่อภาษาไทยซ้ำกัน Closed หรือ Cancelled Activity ไม่ block การสร้างกิจกรรมรหัส/ชื่อเดิมสำหรับครั้งถัดไป
*   **Activity Deletion:** การลบ Activity เป็น soft deletion และทำได้เฉพาะ Activity ที่ยังเป็น Draft และยังไม่มี Activity Session เชื่อมอยู่ เพื่อรักษาประวัติการเข้าร่วมและการประเมิน
*   **Template (แบบแผนการประเมิน):** ชุดการตั้งค่าน้ำหนักคะแนนสมรรถนะของกิจกรรม/รายวิชา สำหรับนำไปกำหนดให้กับนักศึกษาแต่ละ Cohort

*   **Template Lifecycle Status:** A Template can be Draft, Active, or Inactive. Draft Templates are still being configured. Active Templates are ready for use but do not lock the connected Curriculum or Template competency weighting during development. Inactive Templates are temporarily disabled and can be made Active again if their connected Curriculum is Active.
*   **Template Status Transitions:** Template status can transition from Draft to Active, Active to Inactive, and Inactive to Active. Active or Inactive Templates do not return to Draft, and Draft Templates do not become Inactive.
*   **Template Duplication:** Duplicating a Template copies its selected Competencies, Course-Competency mappings, weights, Template Additional Courses, Template Additional Categories, and basic metadata such as description when available. The duplicated Template always starts inactive and must be reviewed before activation. Copied Template Additional Courses and Categories are shown in course management as items inherited from the previous Template and not part of the Curriculum, so Student Development Officers can decide whether to keep, remove, or move them. A normal Course mapping is copied only while the Course still has an active placement in the source Template's owning Curriculum. Mappings for Courses already removed from that Curriculum are ignored silently and do not create a missing-course warning. New Courses in the Curriculum that do not yet have mappings are shown as activation blockers.
*   **Template Duplication Preview:** Before creating a duplicate, the user selects the target Curriculum and the Competency Masters to keep. Courses in a different Curriculum are matched by Course Code; missing source Courses, new target Courses without copied mappings, removed Competencies with affected Course mappings, and newly selected Competencies without weights are shown as non-blocking warnings. The duplicate is created in one transaction with no Cohort Assignment, learner grades, or learner scores copied. A duplicate starts inactive and cannot be activated until the normal Template validation passes.
*   **Template Activation:** A Template can become Active only when its connected Curriculum is Active, at least one Competency is selected, every Course required by the Template, including Curriculum Courses and Template Additional Courses, has at least one Competency mapping, and each Competency's weight distribution across its mapped Courses totals 100%.
*   **Template Competency Association:** A Template selects existing active Competency Masters for its own Curriculum-Cohort scoring configuration. Adding or removing an association never creates, edits, or deletes the global Competency Master.
*   **Template Competency Association Edit Rule:** Associations can be changed for Draft, Active, or Inactive Templates, including when learner course scores exist. Session scores remain outside this configuration rule. Removing an association still requires impact confirmation when it clears mapped course weights.
*   **Template Competency Association Removal:** Removing an associated Competency requires confirmation when it has Course mappings. The association marker and every Course-Competency mapping and weight for that Competency are soft-removed atomically. A Template may temporarily have no associated Competencies, but it cannot become Active until the normal activation rules are satisfied.
*   **Template Competency Weighting:** Competency weights are distributed per Competency across only the Courses mapped to that Competency. A Competency does not need to be mapped to every Course in the Template, but the Courses chosen for that Competency must carry weights totaling 100%.
*   **Template Course Mapping:** Template competency mapping targets a Course as it is placed in the Template's course list, either as a Curriculum Course under its Curriculum Category or as a Template Additional Course under a Curriculum Category or Template Additional Category selected for that Template. Curriculum Categories shown in a Template are live references to the connected Curriculum, so category name changes in Curriculum Management appear in the Template. If a Curriculum Course is moved to another Category, the mapping follows that Curriculum Course placement and the move is managed through Curriculum Management, not Template Management.
*   **Template Deletion:** A Template can be deleted when it is Draft or when it has never been used for real student evaluation. Inactive Templates can be deleted if they have no real student usage.
*   **Template Real Usage:** A Template is considered used for real student evaluation once a student in its assigned Cohort has a course competency score, session competency score, or computed Competency result. One such record is sufficient; the system does not wait for all students or all scoring to complete. Active status means ready for use; real usage means the Template has actually affected student scoring.
*   **Template Edit Rule:** Template mapping, weights, Template Additional Courses, and Template Additional Categories can be edited only while the Template is Inactive. If the Template already has student scores or computed results, editing any of these is an emergency correction that requires recalculation of the affected Cohort.
*   **Template Score Recalculation:** After editing Template mapping, weights, Template Additional Courses, or Template Additional Categories that affect existing student scores, recalculation is a separate explicit action. The user must be warned that recalculation affects every student in the Template's Cohort.
*   **Template Recalculation Required:** When Template mapping, weights, Template Additional Courses, Template Additional Categories, or Template course structure membership change after scores or computed results already exist, the Template is marked as requiring recalculation until the recalculation action completes.
*   **Template Activation With Stale Scores:** A Template that requires recalculation cannot become Active until recalculation completes successfully.
*   **Template Recalculation Failure:** Template score recalculation is all-or-nothing. If recalculation succeeds, the new scores replace the old scores and the Template no longer requires recalculation. If recalculation fails, score changes are rolled back, the Template still requires recalculation, the Template cannot become Active, and the user must see an error before retrying.
*   **Template Recalculation Lock:** While Template score recalculation is running, Template mapping, weights, Template Additional Courses, and Template Additional Categories cannot be edited, recalculation cannot be started again, the Template cannot become Active, and the user interface shows that score recalculation is in progress.
*   **Template Recalculation Completion:** Successful recalculation clears the recalculation-required state but does not automatically make the Template Active. Users must review the result and explicitly activate the Template again.
*   **Template Recalculation Summary:** After recalculation, users see the number of students or cohort members recalculated, course scores updated, competency results updated, recalculation time, and the user who triggered the recalculation.
*   **Template Recalculation Messages:** Missing grades and students without enrollment for not-yet-reached courses are informational states. Missing course competency mapping, incomplete Competency weight totals, and grades without grade maps are warnings. Invalid Templates, deleted Courses or Competencies, and failed score writes are errors.
*   **Template Weight Rule Stability:** The current expected Competency weight total is 100%, but the exact weight rule is still provisional and may change when the scoring policy is clarified.
*   **Template Curriculum Ownership:** A Template belongs to one Curriculum and is configured before it is assigned to a Cohort. A newly created Template can remain unassigned while it is prepared. A Cohort entry year belongs to the Cohort and is not entered when creating a Template. One Curriculum can have many Templates.
*   **Template Curriculum Requirement:** Every newly created Template must select one Curriculum. A legacy Template without a Curriculum is preserved as read-only historical data and cannot be assigned until a dedicated repair workflow exists.
*   **Template Assignment:** A Template Assignment is the explicit relationship that gives one ready Template to one Active Cohort. It uses the Cohort record (`cohort_id`) as its canonical identity rather than an entry year alone. Each Curriculum-Cohort pair has only one live assignment, and one Template can have only one live assignment at a time.
*   **Template Assignment Curriculum Match:** A Template can be assigned only to a Cohort of the same Curriculum. The user interface filters Cohorts accordingly, and the server enforces the same boundary.
*   **Template Assignment Roster Independence:** An Active Cohort can receive a Template Assignment before its student roster is imported. Roster size is shown as operational context and never blocks Assignment.
*   **Template Assignment Access Scope:** Student Development Officers can view and manage Template Assignments only in their own Faculty. Admins can manage every Faculty after explicitly selecting one. Learners and Lecturers cannot access Template Assignments.
*   **Legacy Template Assignment Preservation:** A legacy Template link that cannot be matched to a real Cohort remains an unassigned Template. The system does not create a Cohort automatically or discard the Template's historical configuration.
*   **Legacy Template Assignment Migration:** A legacy Template link becomes a current Assignment only when it matches an existing Active Cohort of the same Curriculum and both the Template and Cohort are Active. All other legacy links preserve Template ownership and history but remain unassigned.
*   **Template Assignment Readiness:** A new Template must be explicitly activated through Template Management before its first assignment. A previously assigned Template with no live Assignment may be selected again after the server validates its Curriculum, Competency configuration, and Core weight totals. If that historical Template is inactive, the assignment transaction reactivates it only after readiness validation succeeds.
*   **Assigned Template Deactivation:** Deactivating an assigned Template for configuration changes keeps its Assignment with the same Cohort. The Assignment shows the Template as temporarily inactive; after validation and reactivation, the same Assignment resumes without reassignment. Only explicit unassignment removes the relationship.
*   **Assigned Template Deletion:** A Template with a live Assignment cannot be deleted. Users must explicitly unassign it first, which preserves Assignment history and makes the Template inactive.
*   **Template Assignment Reuse:** Replacing or removing an Assignment soft-deletes the old relationship and preserves its reason and timestamps. It does not deactivate the old Template and does not make the Template permanently unavailable. When the old Template has no live Assignment, it may be assigned to another Cohort in the same Curriculum and Faculty scope, including returning to the original Cohort.
*   **Template Assignment Flexibility:** During development, replacement and unassignment remain available even when the Cohort already has course or activity scores. Existing grades and scores are preserved. Assignment changes are configuration changes; the Cohort must be marked for explicit score recalculation before its Dashboard is expected to reflect the new Template.
*   **Configuration Change and Historical Scores:** Editing a Curriculum, Template weight, Template competency association, or Competency master does not rewrite historical learner scores or competency results automatically. Users must run a separate recalculation workflow when they need existing results to reflect the new configuration.
*   **Template Assignment Confirmation:** Assigning, replacing, or removing a Template Assignment always requires confirmation that identifies the Template, Curriculum, Cohort entry year, and current roster size.
*   **Template Assignment History:** Each Assignment records who assigned it and when. Replacing or removing an Assignment records who ended it, when it ended, and a required reason in the same Assignment history. This is focused Assignment history, not a full audit-log system.
*   **Template Assignment Calculation Boundary:** Creating, replacing, or removing a Template Assignment never calculates learner course competency scores automatically. Course-score calculation and recalculation are separate workflows that run only after academic records and score rules are ready.
*   **Template Cohort Boundary:** An assigned Cohort cannot be earlier than the Template Curriculum's effective year. Student Development Officers are expected to know this, but the system treats it as a guardrail to prevent invalid Curriculum-Cohort combinations.
*   **Student Cohort Identity:** A Student Cohort is identified by one Curriculum and one entry year. Faculty and Major are derived from that Curriculum; a Major and entry year alone do not identify a Cohort.
*   **Student Import Scope:** Student Management creates or updates student identity and enrollment data only. It does not automatically create learner login accounts; account provisioning and linking to a student identity are a separate workflow.
*   **Student Import Reconciliation:** Student code identifies a student during import. Imports are previewed before saving. A duplicate in the same Cohort is skipped; changes to personal details require an explicit update choice; a different Curriculum or entry year is a conflict that cannot move the student automatically.
*   **Student Cohort Import:** One import targets one selected Cohort. Faculty, Major, Curriculum, and entry year come from that Cohort rather than spreadsheet columns. The required import fields are student code, Thai first name, and Thai last name; English first and last names, email, and phone are optional.
*   **Student Cohort Removal:** Removing a student from a Cohort never deletes the student identity or login account. It is allowed only before the student has course enrollment, attendance, or score data; otherwise the historical Curriculum relationship remains and a separate transfer, withdrawal, or status-change workflow is required.
*   **Student Management Scope:** A Student Development Officer can view and manage Cohorts and students only inside the Officer's Faculty. An Admin can manage every Faculty after explicitly selecting one. Learners cannot access student records, and Lecturers see only Session rosters assigned to them.
*   **Student Cohort Record:** A Student Cohort is a first-class record created before students are imported. It owns its Curriculum and entry year; Faculty and Major are derived from the Curriculum. Student membership is derived from enrollment records rather than duplicated in a separate membership list.
*   **Student Cohort Lifecycle:** A Cohort progresses from Draft to Active to Archived. Draft Cohorts are prepared before use; Active Cohorts are available for student and Template operations; Archived Cohorts preserve history and are read-only.
*   **Student Cohort Uniqueness:** A Curriculum and entry year identify exactly one Cohort. This identity remains reserved after archival or soft deletion; sections, tracks, intake rounds, and special groups are not Cohorts in the current requirement.
*   **Student Cohort Activation:** A Cohort can become Active when its Curriculum is Active and its entry year is set. It may be Active before any students are imported, so its Template can be prepared before the roster arrives.
*   **Student Cohort Curriculum Boundary:** A Cohort entry year must be the same as or later than the effective year of its Curriculum.
*   **Student Cohort Entry-Year Lock:** A Cohort can change its entry year only while it is Draft, empty, and unassigned. Once it has a student or a Template Assignment, the entry year is immutable.
*   **Developer Cohort Curriculum Reassignment:** During the development phase, a Draft or Active Cohort can be moved to another Active Curriculum after an explicit impact confirmation. The reassignment moves live roster Curriculum affiliations, ends the current Template Assignment and makes its Template Inactive, then soft-removes course grades, course score snapshots, Cohort Competency targets, and aggregate Competency results. Attendance and raw Activity scores are preserved. A new Template, new targets, and an explicit recalculation are required before academic results appear again.
*   **Student Cohort Display:** A Cohort display name is derived from its Curriculum code, Curriculum name, and entry year. It has no user-defined code or name in the current requirement, but it may carry an optional internal note.
*   **Student Data Minimization:** Student Management does not collect national ID or passport information in the current requirement. Thai title is optional; student code and Thai first and last names are required, while English names, email, and phone are optional.
*   **Student Management Boundary:** Student Management owns Cohorts, student identity, Curriculum affiliation, and the Cohort Grade Management workspace. Grade Management writes academic grade records only; it does not create REG accounts or connect to an external REG system in v1.
*   **Student Roster Import:** A Cohort roster can be imported from XLSX or CSV using the prescribed header template. The import is previewed and validated before it is committed; the server remains the final validator.
*   **Student Roster Import Atomicity:** A roster import is all-or-nothing. Any unresolved validation error blocks import, and any write failure rolls back the whole roster transaction.
*   **Student Enrollment Status:** Imported and manually added students start with the Student status. Student Management can later record Student, Suspended, Alumni, or Inactive status. Alumni and Inactive students retain history but cannot be added to a new Cohort or register for new activities.
*   **Student Code:** Student code is the immutable identity used for roster import. Regular student editing never changes it; a correction after real usage requires a separate audited workflow.
*   **Active Cohort Roster:** An Active Cohort can accept manually added and imported students, and can update student personal details. Adding a student does not change prior student scores or require recalculation. Archived Cohorts are read-only.
*   **Student Cohort Archive:** A Cohort can be archived only when it has no Student or Suspended members and no Active Template. Archiving preserves roster, score, and Template history while making the Cohort read-only; the system never deactivates a Template automatically. An Admin alone can reactivate an Archived Cohort after confirmation and a required reason; an Officer cannot reactivate it.
*   **Student Cohort Deletion:** A Cohort can be soft-deleted only while it is Draft, empty, and has no Template Assignment. Deletion hides the Cohort without releasing its Curriculum-entry-year identity; it can be restored by a future administrative action.
*   **Course Competency Score Components:** A learner's competency result separates **Core Score** from required Curriculum Courses, **Course Bonus Score** from elective Curriculum Courses and Template Additional Courses, **Activity Score** from finalized Activity Sessions, and **Accumulated Total** (`Core + Course Bonus + Activity`). `final_score` stores the Accumulated Total and is not capped at 100.
*   **Cohort Competency Target:** Each active Cohort owns its Competency targets in `comp_curriculum_requirements`. A learner passes a required Competency when `Course Total` (`Core + Course Bonus`) reaches its Cohort target. Activity Score is visible in accumulated progress and the Radar Chart, but does not satisfy the v1 Curriculum passing target.
*   **Dashboard Course Scope:** The learner Dashboard's Curriculum mode reads Competencies from the Active Template assigned to the learner's Active Cohort. It uses `Course Total` for the Radar Chart and shows the Cohort Curriculum target and passing state.
*   **Dashboard Activity Scope:** The learner Dashboard's Activity mode reads Competencies from finalized Activity Session score results, independently of the learner's Template or current Cohort. It includes only non-deleted, locked Session scores and does not show Curriculum passing criteria.
*   **Accumulated Activity Score:** When a learner receives the same Competency from multiple finalized Activity Sessions, the Dashboard sums every `earned_percent` value. Activity scores are cumulative and are not capped at 100.
*   **Core and Bonus Weight Rule:** Core/Bonus is derived from the Curriculum Course placement, not selected manually in Template Management. Required Courses are Core; elective Courses and Template Additional Courses are Bonus. Each selected Competency needs exactly 100% total Core weight before its Template can become Active. Bonus weights may range from 0 to 100% per mapping and do not need to sum to 100%.
*   **Course Grade Map:** Course scoring uses the fixed grade map `A=100`, `B+=85`, `B=80`, `C+=75`, `C=70`, `D+=65`, `D=60`, `F=0`. Grades `S`, `U`, `W`, and `I` do not produce Course Competency Score records. Retakes use only `crs_course_enrollment.is_best_grade = 1`.
*   **Explicit Course Recalculation:** Editing a Curriculum, assessment-plan mapping, weight, or Competency master never rewrites historical scores automatically. An authorized Officer/Admin explicitly recalculates the Cohort when ready. Recalculation replaces that Cohort's current course score snapshots and recomputes result components in one transaction.
*   **Cohort Grade Record Identity:** A live course grade is unique by `student_curricula_id + course_id + academic_year_be + semester`. Retakes in different academic years or semesters remain separate records.
*   **Cohort Grade Source:** Manual entry stores `grade_source = manual`; Excel import stores `grade_source = excel`; `grade_source = reg` is reserved for a future connector. Source reference is optional and is not a full audit log.
*   **Cohort Grade Import:** Grade Excel imports require `รหัสนักศึกษา`, `รหัสวิชา`, `ปีการศึกษา`, `ภาคเรียน`, and `เกรด`. The server previews Cohort/Curriculum scope, Grade Map, duplicate file rows, and existing-record conflicts before commit. Existing conflicts are replaced only when the user selects them; unselected conflicts are skipped.
*   **Cohort Grade Best Result:** The system marks one live grade per learner-course as `is_best_grade = 1` using the highest fixed Grade Map score. Equal scores use the latest academic year and semester. `S`, `U`, `W`, and `I` remain academic records but do not create Course Competency Score rows.
*   **Cohort Grade Recalculation Flag:** Any manual or Excel grade mutation sets `course_scores_recalculation_required = 1`. Course Competency Scores and learner Dashboard results remain unchanged until an authorized user explicitly recalculates; successful recalculation clears the flag and records `course_scores_recalculated_at`.
